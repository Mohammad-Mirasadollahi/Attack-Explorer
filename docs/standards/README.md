# Attack Explorer — Modular Documentation & Content Authoring Standard System (`MOD-00`)

> **Module ID**: `MOD-00` (Master Router & Architecture Index)  
> **Scope**: All Markdown Engineering Documents (`/docs/**`, `/seo-audit/**`), Attack Scenario Definitions (`/modules/scenarios/**`), Step-by-Step Operational Guides (`/lib/step-guides/**`), Threat Intelligence & Attribution Registries (`/lib/attack-sources-and-legal.ts`, `/lib/threat-intel-service.ts`), SEO/GEO Metadata (`/lib/seo-metadata.ts`), and Workbench UI Copy (`/components/**`).  
> **Status**: Mandatory Permanent Standard · Enforced by `/lib/documentation-standards.ts` and `/lib/documentation-standards.test.ts` for `MOD-00` through `MOD-12`. Includes **`MOD-13`** (Excalidraw technical whiteboards) and **`MOD-14`** (SVG + GSAP silent technical clips).

### Domain layout (engineering rule)

| Layer | Path | Responsibility |
| :--- | :--- | :--- |
| **Domain packages** | `/modules/scenarios/<id>/` | One folder per attack. Required: `scenario.ts`, `index.ts`. Optional: `step-guide.ts`, `standard-patch.ts`, `telemetry.ts`, `choreography.ts`, `three/` |
| **Authoring contracts** | `/modules/scenarios/contracts.ts` | Step-guide and standard-patch types. Packages import these, not `lib/` |
| **Catalog** | `/modules/scenarios/all-*.ts` | Generated by `npm run scenarios:registry`. Do not edit by hand |
| **Legacy drafts** | `/modules/scenarios/legacy/` | Draft schema normalizer only. New scenarios use `AttackScenario` |
| **3D entries** | `/modules/scenarios/three-registry.ts` | Lazy loaders. Package `index.ts` does not export `three/` |
| **App routes** | `/app/scenarios/[id]/` | Next.js pages only |
| **Workbench projection** | `/lib/scenario-step-guides.ts` | Binds domain guides to diagram and simulation engines |
| **UI** | `/components/` | React surfaces. Shared Three.js HUD stays in `/components/three/` |

Import domain code as `@/modules/scenarios/...`. `npm run scenarios:registry` refreshes barrels. The architecture test rejects removed compatibility folders, domain imports of app libraries, and hand-edited catalogs.

## 1. Why Our Documentation Standard Is Modular

Because **Attack Explorer** unifies interactive 2D network diagrams, kernel/process memory maps, raw SIEM/Sysmon telemetry, 3-layer pedagogical narratives, multi-vendor threat intelligence citations, and programmatic SEO/GEO structured data, **a single monolithic style guide cannot govern every artifact effectively**.

Instead, the Attack Explorer Documentation & Content Authoring Standard is architected as **specialized, composable modules (`MOD-01` through `MOD-14`)**. Authors and automated tools load only the modules relevant to their current task while maintaining 100% consistency across the entire platform.

## 5. Programmatic Enforcement & Universal Per-Section Clarity Law (`/lib/documentation-standards.ts`)

Every rule in `MOD-01` through `MOD-12` is backed by executable contracts in [`/lib/documentation-standards.ts`](../../lib/documentation-standards.ts) and [`/lib/section-3d-registry.ts`](../../lib/section-3d-registry.ts), and verified automatically by [`/lib/documentation-standards.test.ts`](../../lib/documentation-standards.test.ts), [`/lib/section-3d-registry.test.ts`](../../lib/section-3d-registry.test.ts), [`/lib/scenario-step-guides.test.ts`](../../lib/scenario-step-guides.test.ts), and [`/lib/inspector-scope.test.ts`](../../lib/inspector-scope.test.ts). **`MOD-13`** is mandatory for any scenario that ships Excalidraw boards; automated board-descriptor tests are planned — until then, use the Process Hollowing reference package and the checklist in `MOD-13` §10. **`MOD-14`** is mandatory for any scenario that ships a technical clip. It standardizes the decision procedure, not a scene stencil. At 1x every teaching change and every hold must meet `clipPace.ts` (`MOD-14` §4.5). Automated clip-decision tests are planned — until then, review against `MOD-14` §9. Study the Process Hollowing clips as filled examples of that procedure. Do not trace their casts onto another section.

**Permanent Universal Per-Section Clarity Law (Enforced Automatically Across Every Section)**:
1. **Prop-Purpose Clarity (`validateStoryPropClarity`)**: Whenever a Story Analogy introduces key props or paired objects (such as *"two golden master keys"*), both the Story prose and `storyMappings[]` must explicitly state what **each** prop unlocks or does—with zero technical jargon in Story text.
2. **Per-Token Inline Plain-English Why (`validateTechnicalSectionInlineClarity`)**: Across **Step and Memory deep-dive** technical blocks (`steps[].simpleExplanation`, `steps[].howItWorksInPractice`, `stages[].description`, and Sequence `underTheHood`), every technical API, syscall, kernel struct, hex flag, handle, or Event ID must carry an immediate plain-English parenthetical explaining **what it is and why it is used**. Dense jargon-dump sentences fail CI automatically. Overview `briefing.plainSummary` is a **roadmap** (`MOD-11` Formula A2), not a Step-level API dump, and is not held to the same API-density gate.
3. **Overview Ownership**: The Inspector tab is labeled **Overview**. Overview must not replay every kill-chain step or host Memory forensics (VAD/`SEC_IMAGE`/`MEM_PRIVATE`); migrate unique Overview facts into Steps/Memory before shortening (see `MOD-11` §7 Migration Protocol).
4. **Inspector Tab Shell (`MOD-12`)**: Cascading Process → Process Hierarchy; VAD → Memory; Stage Filter off Overview; sidebar labels without `(N)` counts; Steps without Auto-Play / legend cards; code under `/components/inspector/**`.
5. **One-Stop Section Gate (`validateSectionFullClarityStandard`)**: Automatically enforced by `validateScenarioAgainstModularStandards()` for every upgraded Step/Memory section so the standard never regresses.
